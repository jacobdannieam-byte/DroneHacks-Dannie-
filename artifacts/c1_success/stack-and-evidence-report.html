3. What actually ran, from simulator to motors

  1. World and vehicle: authored Gazebo calibration geometry and vehicle collision model, launched through hybrid_environment.launch.py and start_px4_in_gazebo.sh. Identity, world and vehicle hashes are captured in the owner/launch files.
  2. Physics and native autopilot: Gazebo dynamics plus PX4 SITL. PX4 retained its estimator, flight-mode logic and low-level position/velocity/attitude/motor control. This did not replace PX4 with a neural controller.
  3. ROS transport: ROS 2 Humble, PX4 message definitions and Micro XRCE-DDS bridge. The isolated owner supplied Offboard heartbeat, trajectory setpoints and vehicle commands.
  4. Sensors: actual Gazebo forward depth images and camera calibration, simulated bottom distance sensor, PX4 estimates/status. Camera tracking was simulated estimator output, not a real visual-inertial estimator processing these images. The EV bridge converted the simulated tracking frame into PX4's expected convention. The depth images prove recorded scene observations, not real VIO qualification.
  5. Decision and command owner: examples/calibration_trial_owner.py and refnav/calibration_trial.py executed a bounded state machine: preflight → climb → settle → straight transit → brake → settle → native LAND → disarm. No Hybrid D0 or PINN model selected commands in C1.
  6. Safety: owner freshness/authority checks, graph checks, height/geofence/speed/deadline checks and native recovery parameters. LAND speed was the specifically approved 0.30 m/s setting; the actual 3D speed cap remained 0.50 m/s. External simulator truth graded the run independently of the command owner.
  7. Evidence: raw ROS bag, PX4 ULog, owner events, actual truth trace, recorder samples, final recorder audit, stopping analysis and command correlation. Capture/receipt timing and bounded deferred recording preserved ordering through graceful shutdown.

C1 did not exercise occupancy-grid waypoint navigation, partial scans, obstacle selection, the full swept-volume clearance gate, learned residuals or end-to-end policy reasoning. It establishes low-speed braking/altitude/landing behavior under this configuration only. It does not qualify stopping from 0.50 m/s, R1 recovery, hardware or the full course.

The static planner and follower themselves are unchanged between the preserved baseline and the inspected current Classical commit; the historical simulator route harness differs only in argument parsing. However, the added live navigation stack changes the default course-run behavior substantially. Comparing “Classical” without naming the execution path and commit would hide this difference.

Current Classical also has limitations directly documented in its code: live navigation does not yet handle openings needing a height change, and it does not correct tracking drift against the map. Its navigation permits proceeding after a five-second settling timeout. These choices need explicit review before borrowing them into the stricter Hybrid trial contract; this report does not silently adopt or change them.

5. What the Hybrid comparison proves so far

The offline comparison uses the protected Classical archive, actual D5 candidate generation, D0 and residual-model seeds 11/29/47. Across 44 synthetic start/goal cases per variant (220 rows), every case found at least one diagnostically eligible candidate. That is candidate feasibility, not a closed-loop mission success rate or native clearance qualification. Host p95 scoring of roughly 18 ms for D0 and 27–28 ms for PINN is not an Orin/ROS real-time guarantee.

The intended DATT-inspired role is a fast physics-based state predictor supporting geometry and a single native owner. It is not a replacement for the autopilot, and the residual network is not a standalone policy. A fair paired flight comparison still needs matching world, vehicle, sensor model, route, launch, limits, recovery, scoring and termination across Classical, D0 and PINN.

6. Remaining gates and interpretation

  1. Use this C1 artifact only for its measured 0.20 m/s braking condition. Complete the separately bounded R1/recovery qualification and any stopping evidence required for higher permitted operating speed.
  2. Finish native launch-contact-to-airborne clearance and directional uncertainty integration for the waypoint path; establish landing coverage under the same geometry and sensor contracts.
  3. Prepare matching bounded waypoint trials with registration off, first using the Classical-derived simple map route and D0. Review the exact command owner, limited-look behavior, stale-map/unknown-space handling and recovery before granting moving authority.
  4. Keep PINN shadow-only until paired native timing and prediction-error evidence supports promotion. C1 cannot clear these gates on its own.
